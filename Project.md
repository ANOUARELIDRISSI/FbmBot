# 🇧🇪 BE-CarScout — Belgian Used-Car Deal Finder

A personal pipeline that watches Facebook Marketplace for used cars in Belgium, understands each listing (not just its numbers, but what the seller *actually wrote*), scores it against the real market, and only pings you on Telegram when something is genuinely worth looking at. Over time it learns from your own 👍/👎 verdicts what "good" means to you specifically.

## Why this exists

Marketplace is full of noise: bad prices, rebuilt-title exports, cars "for parts" mislabeled as running, and vague descriptions that hide real mechanical issues. Scrolling manually doesn't scale, and a plain price/km filter is too dumb to catch the good stuff — you also can't just have an LLM "read and decide," because it hallucinates and doesn't have a consistent standard. The goal here is to split the work the way a smart human would: extract facts → understand the free text → score it against the market → only surface real opportunities.

## Scope (v1)

Belgium only, to start. Rather than build something generic for all of Europe, the point of v1 is to build a system that actually understands the Belgian used-car market — regional wording (NL/FR), local paperwork terms (*keuring / contrôle technique*, *carnet d'entretien*, CO₂ malus, BTW/margin vehicles), typical price bands per make/model/year in this market, and common phrasing patterns Belgian sellers use.

## Pipeline

```
Facebook Marketplace
        │
        ▼
   [1] Scraper           → raw listing (title, price, km, year, location, description, photos, url)
        │
        ▼
   [2] Structurer         → normalized fields (make, model, variant, fuel, transmission, options)
        │
        ▼
   [3] LLM Description Analyzer
        │   - parses free text (BE-NL / FR / mixed / abbreviations)
        │   - flags mechanical & administrative signals
        │   - outputs structured JSON, not prose
        ▼
   [4] Scoring Engine (rule-based, not LLM)
        │   - price vs. market baseline for that make/model/year/km
        │   - penalties/bonuses from step 3's flags
        │   - confidence score based on data completeness
        ▼
   [5] Decision Gate       → only listings above threshold continue
        │
        ▼
   [6] Telegram Bot        → sends opportunity card + 👍/👎 buttons
        │
        ▼
   [7] Feedback Store      → your verdicts saved and fed back into scoring weights
```

### 1. Scraper — ✅ Done (2026-09-04)
Pulls listings from Facebook Marketplace for configured search terms/locations in Belgium (Playwright-based; this part is largely a solved problem — several open-source scrapers already do this well). Outputs raw listing data on a schedule.

**Code:** `src/becarscout/scraper/` — `models.py` (the `RawListing` schema), `belgium.py` (hub cities/search config), `session.py` (login), `facebook_marketplace.py` (the scraper itself). CLI: `uv run becarscout login` / `uv run becarscout scrape`. Output: `data/raw/listings_<timestamp>.jsonl`.

**How it was built, in short:**
- **Login**: Facebook's login form is never automated (fastest way to get an account flagged). `becarscout login` launches a real, visible Chromium window backed by a persistent profile directory (`data/.session/profile/`) and just idles — a human logs in normally, cookies land on disk continuously, no explicit export step. Every later scrape reuses that same profile directory.
- **Coverage**: Facebook Marketplace search is radius-based from one point, not country-based, so Belgium is covered by fanning out over 5 hub cities (Brussels, Antwerp, Ghent, Liège, Charleroi) with overlapping radius and deduping by listing id (`belgium.py`).
- **The grid vs. the detail page**: Facebook's search-results cards turned out to expose only price + location, no title at all (confirmed by inspecting live rendered HTML, not assumed) — so the grid pass is used purely for link discovery. Every listing is then visited individually for the real title (the last `<h1>` on the page — the first is generic chrome like "Notifications"), price, location, description, and photos. This is slower (~76 listings ≈ 11 minutes) but far more reliable.
- **Description extraction**: raw Facebook HTML is packed with nav/sidebar/"today's picks" boilerplate. Rather than hand-picking brittle selectors for it, the detail page's full HTML is run through `trafilatura`, which strips the boilerplate on its own; a small anchor-based trim (cut between the "Seller's description" heading and the "Seller information" block) removes the last few Facebook-UI fragments trafilatura leaves behind.
- **Belgium ↔ elsewhere sanity check**: confirmed Facebook honors the location slug in the URL (not the account's real/IP-detected location) by pointing the same code at Rabat, Morocco and getting back genuine Moroccan listings in MAD.
- **Cars-only filtering**: Facebook's `vehicleType=car_truck` query param does **not** reliably exclude other vehicle types — boats and motorcycles leaked through in testing. Most listings also don't fill in structured fields (mileage/transmission/etc.) that could otherwise distinguish a car from a boat. Current filter is a blunt but auditable keyword check against the title (`_NON_CAR_TITLE_KEYWORDS` in `facebook_marketplace.py`) — generic terms (moto, bateau, remorque, camping-car, ...) plus a short list of unambiguous motorcycle/boat *brand* names added after two slipped through in testing (a "Jeanneau" boat, a "Kawasaki" motorcycle — "Suzuki"/"Honda" deliberately excluded from that brand list since they also make cars). Still not exhaustive — real classification belongs in stage 3 (LLM analyzer); this is just a coarse backstop.
- **Known limitations / things to revisit**: (1) brand-name non-car leakage, per above — still possible for less-common brands; (2) Facebook's markup uses hashed/auto-generated class names that change often — selectors lean on structural hooks (link hrefs, last-`<h1>`, span ordering) but will likely need upkeep; (3) detail-fetching is sequential, not parallelized; (4) a pure description-only edit (price unchanged) on an already-known listing isn't detectable — see "Price/description change detection" below for why, and what is covered.

**Price/description change detection — added 2026-09-05**: previously, once a listing_id was known, it was frozen forever — `upsert_raw_listings` only ever inserted new rows, so a seller lowering their price or editing their description after the first scrape was never noticed. Fixed without reintroducing the cost `known_ids` exists to avoid (revisiting every known listing's detail page every run): the grid pass already exposes a price for every card, known or not, so `scrape_belgium_cars` now compares each known listing's grid-observed price against what's stored (`db/repository.get_known_price_texts`) using *parsed* numbers, not raw text (`_prices_differ`, `structurer/parse.parse_price`) — a grid-vs-detail-page formatting difference for the exact same price (e.g. "8.500" vs "8 500") must never be mistaken for a real change. Only listings whose price actually changed get a detail-page revisit — which also refreshes the description and photos in that same visit, so an edited post gets picked up too, not just a new number. `db/repository.update_changed_listing` then resets `structured_at`/`scored_at`/`notified_at` so the listing flows back through the pipeline as a fresh scoring pass (and a genuine re-notification if it now scores differently) — but only resets `analyzed_at` (forcing a fresh Mistral call) if the description text actually changed, not on every price-only update, to avoid spending an LLM call for no reason. Also re-validates `is_whole_vehicle` and every other stage-3 signal automatically whenever the description does change, since that just re-runs stage 3 from scratch. **Honest limitation**: a listing whose *description* changes but price stays exactly the same isn't caught — there's no cheap, grid-level signal for that, and re-checking every known listing's detail page to catch it would defeat the entire point of `known_ids`. 5 new tests (`tests/scraper/test_facebook_marketplace.py`, `tests/db/test_repository.py`).

**Real bug found the same day, on the very first live run**: the first real scrape after shipping this reported "22 with a changed price" out of 29 known listings — implausibly high for one hourly gap. Investigating a few by hand (comparing the DB's already-computed `price_eur` against the new grid-observed price) showed the numbers were often *identical* — no real change at all. Root cause: the comparison used the **grid's** price extraction as ground truth, but stage 1's own docstring already documents that the grid card "can't be trusted for any of these beyond a rough price/location fallback" (`_extract_cards`'s `lines[-2]` heuristic) — reliable enough for brand-new listings (where it's immediately overwritten by the authoritative detail-page fetch) but not as a standalone signal for already-indexed ones. Fixed by treating a grid mismatch as a *candidate* only: the detail-page revisit that candidate triggers now also re-confirms the price against what's stored, and the change is only accepted (triggering re-score/re-notify) if the *detail-page* price actually disagrees too — roughly 3 in 4 candidates that day turned out unchanged once confirmed. Also had to hand-repair ~32 rows in the live DB whose `structured_at`/`scored_at`/`notified_at` had already been reset by the false positives before the fix landed — worth noting this accidentally surfaced a separate, real gap: several of those rows (including the original 1986 Ford F-150 from this same stage's bug report above) had never been re-scored since the year-cascade/`is_whole_vehicle` fixes shipped, because this project's incremental processing only ever touches rows with `scored_at IS NULL` — a code fix alone does **not** retroactively correct an already-cached bad score. Deliberately let those 32 rows re-flow through the real pipeline instead of just restoring their stale timestamps, confirming live that the F-150 now correctly scores 0 (`is_whole_vehicle=False`) instead of the original +72.

**Salvaged for later (not yet wired in):** `src/becarscout/bot/` holds a working Telegram bot skeleton (conversation-based preference collection, SQLAlchemy models, Alembic migrations) recovered from an earlier prototype repo before it was discarded — real infrastructure for stage 6, but not touched yet. It won't run as-is: needs `uv add python-telegram-bot sqlalchemy alembic openai nest-asyncio` and a `.env` with `TELEGRAM_BOT_TOKEN` first.

### 2. Structurer — ✅ Done (2026-09-04)
Cleans and normalizes what can be extracted deterministically: price, mileage, year, make/model, fuel type, transmission, seller location, listing age, photo count.

**Code:** `src/becarscout/structurer/` — `models.py` (the `StructuredListing` schema), `makes.py` (curated Belgian-market make list), `parse.py` (standalone, individually-testable regex/keyword parsers — one function per field), `structurer.py` (combines them into `structure_listing`/`structure_listings`). CLI: `uv run becarscout structure [--input path]` (defaults to the most recent `data/raw/listings_*.jsonl`). Output: `data/structured/structured_<timestamp>.jsonl`.

**How it was built, in short:**
- **Price**: strip everything but digits from `price_text`; "Free" → `price_eur=0, is_free=True`.
- **Year**: regex for a standalone 4-digit token in the plausible car-year range, checked against title then description (avoids matching inside a longer number like a mileage figure).
- **Mileage**: regex anchored on the literal "km" token, both orders ("112000km" and "km 219000"), with a sanity bound (10–1,000,000) to reject false positives.
- **Fuel type / transmission**: keyword lists covering BE-NL/FR/EN terms (e.g. "essence"/"benzine"/"petrol", "automaat"/"automatique"/"dsg"), checked in a fixed priority order (electric → hybrid → lpg → diesel → petrol) so rarer/more-specific terms win over generic ones.
- **Make/model**: a curated flat list of ~50 makes realistic for the Belgian market (`makes.py`) — deliberately **not** the salvaged `bot/models/marksmakes.py` list, which is US-market-focused and missing Citroën/Renault/Peugeot/etc. Matched by literal word-boundary search in the title first, then description; `model_hint` is just the text following the make in the title, not a validated model name.
- **Location**: split `"City, REGION"` on the comma (REGION is VLG/WAL/BRU as Facebook shows it).
- **Listing age**: parses Facebook's own relative-time phrase ("Listed a week ago", "Just listed") into approximate days — this required a small stage-1 addition (`RawListing.listed_relative_text`, captured alongside price/location on the detail page) since the scraper wasn't retaining that text before.

**Validated against the real 76-listing Belgium dataset from stage 1** (`data/raw/listings_20260904T045935Z.jsonl`) — extraction rates: price 100%, location 100%, year 56%, make 36%, fuel type 32%, mileage 21%, transmission 18%. `listing_age_days` was 0% on that file since it predates the `listed_relative_text` capture; will populate on the next scrape.

**Known limitations:**
- Make/model detection only works when the make is spelled out somewhere in the text — "Golf 6" alone won't resolve to Volkswagen without a maintained model→make catalogue (out of scope for now; a plain regex pass shouldn't try to be a car database).
- No fuzzy matching — a seller typo like "Metcedes" won't match "Mercedes".
- All of the low-yield fields (mileage, fuel, transmission) are exactly the kind of information often buried in free-text descriptions in ways a regex can't reliably parse ("5 versnelling bak" implies manual but was never explicitly said) — that gap is what stage 3 (LLM analyzer) exists to close.

**Real bug found via live Telegram output, fixed 2026-09-05**: several listings showed implausible 300-500km mileages on cars from the 1980s-2000s. Root cause, found by pulling the raw stored text for the offending listings straight out of the DB: `_MILEAGE_BEFORE_RE`'s `[:\s]+` gap allowed matching *across newlines*, bridging Facebook's own "within a 64 km radius" UI boilerplate to an unrelated sidebar listing's price several lines below it (`"...64 km\n500 $US..."` → extracted as 500km). A third listing's regex correctly matched digits+"km" but grabbed the wrong occurrence — a mid-description repair anecdote ("après 300km la distribution a cassé") — instead of the actual odometer figure stated earlier as "209mille km" (French "thousand", which the old regex didn't parse as a number at all since "mille" isn't a digit). Fixed in `parse.py`: the gap in `_MILEAGE_BEFORE_RE` is now restricted to spaces/tabs only (no newlines), a new `_MILEAGE_MILLE_RE` handles "X mille km" phrasing and is tried first, and a new `sanity_check_mileage()` (wired into `structure_listing`) discards any extracted mileage under 1,000km on a car that isn't genuinely this model year and whose text doesn't say "0 km"/"neuf(ve)"/"nieuw(e)"/"new" — a safety net against the next mis-extraction of this shape, not just these three. Regression tests in `tests/structurer/test_parse.py` use the actual raw text from the three affected listings as fixtures.

### 3. LLM Description Analyzer — ✅ Done (2026-09-04)
This is the part a keyword filter can't do. The description is fed to an LLM with a strict extraction prompt so it returns **structured fields, not opinions** — for example:

| Raw phrase (BE listing) | Extracted signal |
|---|---|
| "motor lampje soms aan" | `warning_light: true, severity: unknown, needs_diagnostic: true` |
| "versnellingsbak heeft aandacht nodig" | `gearbox_issue: true, severity: likely_major` |
| "voor export" | `for_export: true` → usually correlates with hidden issues or non-BE paperwork |
| "nieuwe distributieriem" | `timing_belt_replaced: true` → positive signal, reduces near-term risk |
| "keuringsbewijs aanwezig" | `inspection_valid: true` |
| "carnet d'entretien complet" | `service_history: complete` |
| "geen BTW / marge voertuig" | `vat_scheme: margin` (affects resale/export math) |

The LLM's *only* job here is translation from unstructured text to structured facts, plus a rough severity/confidence estimate — it does **not** decide whether the car is a good deal. That judgment call is reserved for step 4, which is deterministic and auditable.

**Code:** `src/becarscout/analyzer/` — `models.py` (`DescriptionSignalFields`/`DescriptionSignals`), `schema.py` (the hand-written strict JSON schema + system prompt), `analyzer.py` (`analyze_description`/`analyze_descriptions`). CLI: `uv run becarscout analyze [--input path] [--model name] [--delay seconds] [--limit N]` (defaults to the most recent `data/structured/structured_*.jsonl`). Output: `data/analyzed/analyzed_<timestamp>.jsonl`, joinable back to structured listings by `listing_id`.

**How it was built, in short:**
- **Provider**: Mistral (user's explicit choice over Claude/GPT), via the official `mistralai` Python SDK. Note for future sessions: the installed SDK version (2.9.4+) has no top-level package re-export — the correct import is `from mistralai.client import Mistral`, not `from mistralai import Mistral` as older docs/training data would suggest. Verified this against the actual installed package structure rather than assuming, since the API surface has grown substantially (agents, conversations, connectors, realtime, etc.) since general knowledge of this SDK was last current.
- **Model gating discovered live**: `mistral-small-latest` returned a hard 429 on every attempt (including after 90s backoffs) on this account, while `ministral-8b-latest` worked immediately — looks like a paid-tier gate rather than per-request throttling. Default model is `ministral-8b-latest`, overridable via `MISTRAL_MODEL` env var or `--model` if the account is upgraded later.
- **Structured output**: uses `response_format={"type": "json_schema", "json_schema": {..., "strict": True}}` with a hand-written schema dict in `schema.py` (kept in sync with `models.py` manually) rather than `DescriptionSignalFields.model_json_schema()`, because Mistral's strict mode requires every property listed in `required` (nullable ones included) and `additionalProperties: false` at every level — Pydantic's default schema output isn't shaped that way out of the box.
- **Resilience**: retries only on an actual 429 (checked via `SDKError.raw_response.status_code`, not string-matching), with backoff; any other failure (bad JSON, schema mismatch, auth) fails fast and falls back to an all-defaults `DescriptionSignals(extraction_failed=True, confidence="low")` rather than crashing the whole batch. A 1-second delay between sequential calls is the default (`--delay`) to stay clear of per-minute limits — batches run unattended, so correctness matters more than throughput.
- **Validated against 5 real listings** from the stage 1/2 test data — extraction quality was genuinely good: correctly recognized that a parts listing's "gearbox already removed" isn't a `gearbox_issue` (per an explicit instruction in the prompt to prevent that specific false positive), pulled `gearbox_issue_severity: likely_major` out of French free text ("Problème de boîte de vitesses"), and cross-checked fuel/transmission/mileage against stage 2's regex results. One observed miss: a misspelled "essance" (should be "essence"/petrol) wasn't picked up as `fuel_type` — LLM extraction isn't immune to unusual typos either.

**Real bug found via live Telegram output, fixed 2026-09-05**: a listing titled "2006 Subaru outback" scored +58 ("97% below market" against a €9,500 baseline) at a €300 asking price — the description actually read "Seats for 2006-2008 Subaru outback... 300 for all". It was a parts listing (car seats), not a car at all, and nothing about the title gave that away. This is exactly the gap stage 1's own known-limitations note anticipated ("real classification belongs in stage 3 (LLM analyzer)") but stage 3's schema never actually got a field for it. Added `is_whole_vehicle: bool` (default `True`) to `DescriptionSignalFields`/`schema.py`'s JSON schema + system prompt — false only when the description makes clear no vehicle is actually included (parts/seats/wheels/engine sold on their own), not when a whole non-running car is explicitly sold "for parts." `scoring.py`'s `score_listing` now short-circuits to `score=0` when this is false, before any price/condition scoring happens. A companion bug in the price floor was fixed alongside it: `_MIN_PLAUSIBLE_CAR_PRICE_EUR`'s check was `price_eur < 300`, so a price of *exactly* €300 (this listing's price) slipped past the guard entirely — changed to `<=`. Added `tests/analyzer/test_schema.py` to catch the next time a model field and the hand-written JSON schema drift out of sync (this fix touched exactly that risk), plus regression tests in `tests/scoring/test_scoring.py` using this real case.

### 4. Scoring Engine — ✅ Done (2026-09-04)
A rules-based model — not an LLM — combines:
- **Price gap**: listed price vs. expected price for that make/model/year/mileage (regression or lookup table built from historical BE listings)
- **Condition adjustments**: bonuses/penalties from the structured flags in step 3 (e.g. confirmed timing belt replacement = +, unresolved warning light = −, "for export" = − unless the user is specifically looking to export)
- **Data confidence**: listings with vague/missing info are down-weighted rather than excluded, since a great deal with a bad description is still worth a look at a lower confidence tier
- **Personal weights**: adjustable per-signal weights that get tuned from your feedback (step 7)

Output: a single opportunity score (and the reasoning trail behind it), not a black-box "yes/no."

**Code:** `src/becarscout/pricing/` (the price-baseline half) — `models.py` (`Comp`/`PriceBaseline`), `comps_2dehands.py` (the comps scraper + disk cache), `baseline.py` (year/mileage-cascaded median). `src/becarscout/scoring/` (the scoring half) — `scoring.py` (`score_listing`, all point-weight constants live at the top of this file), `pipeline.py` (joins structured + signals + baseline per listing), `models.py` (`ScoredListing`). CLI: `uv run becarscout score [--structured path] [--signals path] [--threshold N]`. Output: `data/scored/scored_<timestamp>.jsonl`, every listing included with an `above_threshold` flag (not just the ones that passed).

**How it was built, in short:**
- **Where the "expected price" comes from** — this was the open question going in. Considered three options: (a) accumulate our own historical Marketplace scrapes over time and bucket by make/model/year, (b) scrape a second site with structured, filterable listings for live comps, (c) live web search per listing. Went with (b): **AutoScout24.be and Gocar.be both returned a hard 403** (real bot-detection, not worth fighting), but **2dehands.be** (Belgium's major classifieds site) returned clean 200s — and its search results already carry price/year/mileage/fuel/transmission directly in the grid, no detail-page visit needed per comp, unlike the Facebook scraper. (a) is still worth doing later as a free-over-time supplement per the original v4 roadmap item below; (c) was set aside — turning search snippets into a number needs either another LLM call (reintroducing judgment into a step meant to stay deterministic) or fragile parsing, for a noisier result than (b).
- **Baseline matching**: comps are filtered by year (±2, widened to ±4 if that's under 2 matches) *and* mileage (±40%, widened to ±70%) with graceful fallback to the unfiltered pool at each step — added after the first version (year-only) pulled in a 2021 Golf 8 alongside a 219,000km 2013 Golf 6 and skewed the median up. Median is computed with light outlier trimming (drop the single highest/lowest) once there are ≥5 comps.
- **Two real data-quality bugs found by actually running it on the 76 real listings**, not by inspection: (1) a network timeout fetching comps for one listing crashed the *entire batch* — fixed with per-listing try/except that falls back to "no baseline" and logs, matching the resilience pattern already used in the scraper and analyzer; (2) several listings priced at literal €0/€1 (Marketplace's "make an offer" placeholder pricing) were scoring as extreme "steals" (+100, +118) since the price-gap formula read that as "100% below market" — fixed with a €300 floor below which price-gap is skipped entirely (parts listings and placeholder prices aren't comparable to whole-car comps). A few genuine seller data-entry errors (a 2006 Peugeot 407 listed at €31,000) also produced enormous scores (-1165); these are directionally correct ("steer away") but were clamped to ±150 so one typo doesn't dominate the output.
- **Performance**: originally launched a fresh Chromium instance per comps fetch; refactored to share one browser across an entire scoring run once the crash above surfaced how many fetches actually happen per run.
- **Result on the real dataset**: of 76 listings, 5 scored above the default threshold of 20 after all fixes — each with a full reasoning trail (e.g. `"Priced €850 vs. €4,970 median (83% below market, n=8 comps, high confidence) -> +82.9"` followed by any condition adjustments). Confirms the end-to-end pipeline (scrape → structure → analyze → score) produces genuinely differentiated, explainable output on real data, not just on synthetic test cases.

**Known limitations:**
- Comps search only tries the first word of the structurer's `model_hint` as the model name (e.g. "Mondeo" out of "Mondeo 2.0 diesel 2013 automatic") — works for most European car names but not perfectly.
- No baseline at all for the ~64% of listings where stage 2 couldn't detect a make (see stage 2's limitations) — these score on condition signals alone.
- Point weights in `scoring.py` (e.g. gearbox issue = -40, timing belt replaced = +12) are reasoned first-pass numbers, not tuned against real outcomes — that's explicitly what stage 7's feedback loop exists to eventually correct.

**Second price-comps source added, 2026-09-05**: `pricing/comps_2dehands.py` now also queries **2ememain.be**, merging results by ad id (`_ad_id`, `_fetch_from_all_sites`) — a real coverage improvement (catches ads that rank differently per language's search index), but **not independent validation**: inspecting live ad ids proved 2dehands.be and 2ememain.be are the same underlying database (Adevinta Belgium runs both as a bilingual front-end over one shared inventory — the exact same numeric ad id turns up on both for the same car). Worth being honest about this rather than overselling it as "cross-checked against multiple sites" — a genuinely independent second source would still need AutoScout24.be or Gocar.be to stop blocking (both hard-403 automated access, per stage 4's original notes above), or a different site entirely; neither has been re-attempted. One site failing (blocked, markup changed) no longer sinks the whole comps fetch — whatever the other returns is used as-is, which also quietly improves on the old single-point-of-failure design.
- A `likely_major` condition signal (medium+ confidence) is still fully offsettable by a large enough price gap — e.g. a car with a seller-stated "needs a clutch module" can still clear the gate on price alone. Flagged, not fixed: whether a serious mechanical issue should *cap* the achievable score outright (rather than just being one more weighted input) is a product decision about how risk-averse this system should be, not a pure bug — needs a decision on what the cap should be and whether it applies pipeline-wide or only above some severity/confidence combination before it's worth implementing.

**Real bug found via live Telegram output, fixed 2026-09-05**: a 1986 Ford F-150 (base trim, €8,000 asking) scored +72 as "72% below market" against a median of €29,000 from 19 comps — but the Belgian/US F-150 market for that model name today is dominated by modern trucks (mostly Raptor trim, €30k-€100k+), so the comp pool was comparing a 40-year-old classic against an entirely different vehicle generation. Root cause: `compute_baseline`'s year cascade (`baseline.py`) already filtered by year at ±2 and ±4, but when *neither* found 2+ matches it fell back to the **entire unfiltered comp pool** — silently reintroducing every era-mismatched comp it had just tried to filter out. Fixed by adding a third, final ±8-year tier and making it the floor: if even that finds nothing, the baseline is now reported as "no data" (`median_price_eur=None`, `confidence="none"`) rather than fabricated from a different vehicle generation. Also added a `_MAX_PRICE_RATIO` (5x) sanity guard — if the matched comp pool's highest price is still more than 5x its lowest (a handful of comps that survived year filtering but span incompatible trims), extreme values are trimmed toward that ratio before computing the median, and confidence is forced to "low" if trimming still can't bring it under the threshold, regardless of sample size. Regression tests in `tests/pricing/test_baseline.py` cover the mixed-era case, a tight/consistent pool (unaffected), and the variance guard.

### 5. Decision Gate — ✅ Done (2026-09-04)
Only listings above a configurable score threshold get pushed further — this is what keeps Telegram from turning into spam.

**Code:** `src/becarscout/scoring/gate.py` — deliberately trivial, exactly per the design principle above: `apply_decision_gate(scored, threshold, min_year)`. Default threshold is 20 (`--threshold`); **default `min_year` is 2010** (`--min-year`, or `--no-min-year` to disable) — cars from that year or older never clear the gate regardless of score. This is a stated preference, not a scoring judgment: a 2005 car can still be a genuinely great price-vs-market deal, it just won't reach Telegram. A listing with no detected year still passes — stage 2 misses the year on plenty of genuine listings (see stage 2's limitations), and an extraction gap shouldn't be treated as "too old."

**Next step:** stage 6, the Telegram Bot — wire the salvaged bot skeleton (`src/becarscout/bot/`) to send a card per `ScoredListing` where `above_threshold` is true, using the `reasoning` list as the "why this scored well" text. Needs `uv add python-telegram-bot sqlalchemy alembic openai nest-asyncio` (the bot skeleton's dependencies were never added, since it wasn't wired in until now) and a `.env` `TELEGRAM_BOT_TOKEN`.

### 6. Telegram Bot — ✅ Done (2026-09-04)
Sends a compact card per opportunity: photo, price, key stats, the 2–3 sentence "why this scored well/what to watch out for," and a link — with inline 👍/👎 buttons.

**Code:** `src/becarscout/notifier/` — `formatting.py` (renders a `ScoredListing`'s existing reasoning trail into the card, no new interpretation), `bot.py` (`send_new_opportunities`, `run_feedback_listener`, `find_chat_ids`), `feedback.py` (verdict capture). CLI: `uv run becarscout notify` (send) and `uv run becarscout listen` (a separate, standing process that catches button presses) and `uv run becarscout whoami` (finds your `TELEGRAM_CHAT_ID` after you message the bot once).

**How it was built, in short:** deliberately *not* built on the salvaged `src/becarscout/bot/` skeleton — that was a conversational preference-picker UI (brand/model selection via chat menus, seller negotiation, KBB pricing) for an entirely different, unrelated product idea, and retrofitting it would mean fighting its structure for no benefit. This is a small, purpose-built module instead, matching exactly what this stage actually needs. `.env` needs `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`.

**Made more interactive, 2026-09-05**: the default card used to dump the full point-by-point reasoning trail every time — a wall of numbers before you'd even glanced at the price. Split into two layers instead: the default card now shows fuel type/transmission (stage 2 already extracted these; they just weren't wired into the card) alongside price/year/mileage, plus plain-language, no-numbers condition highlights (`scoring.py`'s new `_condition_highlights`, e.g. "⚠️ Warning light mentioned", "✅ New timing belt", "📦 Listed for export" — mirroring the same flags `_condition_component` scores, just worded for a person instead of an audit log). A third inline button, "ℹ️ Why?", sends the full numeric breakdown (`formatting.py`'s `format_score_explanation` — what used to always be in the card) as a follow-up message on demand, without removing the 👍/👎 buttons. Required one small schema change: `condition_highlights` needed a new DB column (`condition_highlights_json`) on an already-populated production table — since there's no Alembic wired to this schema yet (see next_version.md), added a tiny additive-migration helper (`db/engine.py`'s `_ensure_column`, checks `PRAGMA table_info` and runs `ALTER TABLE ... ADD COLUMN` only if missing) rather than pulling in a full migration framework for one column.

**Real bug found via live send, fixed 2026-09-05**: `becarscout notify` sent 0 opportunities in one real run despite several being genuinely queued — `telegram.error.BadRequest: Can't parse entities: can't find end of the entity starting at byte offset 70`. Root cause: a real seller had titled their listing "...carpass \*130.000 km\*" — the literal asterisks, after `formatting.py`'s escaping and the card's own wrapping `*bold*` markers, produced an escaped-asterisk-then-real-asterisk sequence (`\**`) that Telegram's legacy Markdown parser doesn't reliably handle even though the Bot API docs say `\*` is valid escaping. Scraped titles are seller-written free text and can contain literally anything — trying to safely escape arbitrary text for a parser with fragile, under-documented edge cases is the wrong fight to keep having. Fixed by dropping `parse_mode` entirely: every Telegram message (`formatting.py`, `bot.py`) is now plain text, so there's no delimiter syntax left to break — `_escape()` is gone, titles pass through completely untouched. Validated against the real problematic listing (and 5 others) after the fix: all sent successfully. Cost: bold/italic styling in the card, which was cosmetic — reliability mattered more here.

**Known limitation:** no photo in the card yet (Project.md's spec mentions one) — text-only for now; `listing.photo_urls[0]` is available whenever this gets added.

### 7. Feedback Loop — ✅ Done (2026-09-05), human-approved, not automatic
Your 👍/👎 on each card is remembered, and a small LangGraph agent periodically turns accumulated feedback into a plain-English report of patterns plus concrete *suggested* scoring weight changes. As of the `/validate` command below, those suggestions can be applied for real from Telegram — but only when you explicitly ask for it; nothing changes on its own.

**Code:** `src/becarscout/feedback_agent/` — `memory.py` (mem0-backed storage/retrieval of feedback, fully local), `graph.py` (the LangGraph review agent), `apply.py` (`/validate`'s actual apply step). CLI: `uv run becarscout feedback-review`.

**How it was built, in short:**
- **The raw log stays**: `notifier/feedback.py`'s flat `data/feedback/feedback.jsonl` (listing_id, verdict, timestamp) is unchanged — still the source-of-truth audit trail. mem0 sits alongside it, turning the same verdicts into something *query-able by similarity* rather than just an append-only file.
- **mem0, fully local**: a Chroma vector store on disk (`data/mem0/`) plus FastEmbed (a small ONNX embedding model, CPU-only, downloaded once — baked into the Docker image at build time, same reasoning as installing Chromium ahead of time rather than on first use) for embeddings. No OpenAI key, no data leaving the machine for storage/retrieval. The one network call is to Mistral (via `litellm`, which mem0 uses as a generic LLM backend) for mem0's own internal fact-extraction step when a memory is added — reuses `MISTRAL_API_KEY`, no second LLM provider.
- **Two integration points, both additive**:
  1. **At notify time** (`notifier/bot.py`): before a new opportunity is sent, `find_similar_feedback` checks mem0 for similar-sounding cars you've rated before, and the card gets one extra line ("2 similar cars you liked before") if there's a match. This never changes the score — see `formatting.py`'s `_similar_feedback_note`.
  2. **On every 👍/👎** (`notifier/bot.py`'s callback handler): the verdict is looked up against its full DB row (`db/repository.get_scored_listing`) and stored as a memory describing that car (make/model/year/price/mileage/market median/score **and its condition-signal reasoning trail** — without the reasoning text, the review agent could never notice a pattern like "you keep disliking cars with unresolved warning lights").
- **The review agent itself** (`graph.py`) is a 4-node LangGraph graph: `load_memories` → (conditional: enough volume?) → `synthesize` → `write_report`, or straight to `not_enough_data` if fewer than `_MIN_FEEDBACK_FOR_REVIEW` (5) verdicts exist yet — below that, any "pattern" is noise dressed up as insight. `synthesize` calls Mistral with the actual current `scoring.py` constant values injected into the prompt (found this the hard way in testing: without them, the model guessed plausible-looking but wrong "current" values, e.g. reporting `_WARNING_LIGHT_NEEDS_DIAGNOSTIC` as "-10" when it's actually -20) and a description of what each tunable constant actually controls, so it can't repurpose one for something it doesn't mean (e.g. it initially tried to use `_MIN_PLAUSIBLE_CAR_PRICE_EUR`, a placeholder-pricing sanity floor, to express "the user prefers pricier cars" — fixed by spelling out each constant's real meaning in the prompt).
- **A real Windows bug found while testing this**: printing the review report (LLM-generated markdown, not fully within our control character-wise) via a plain `print()` crashed with `UnicodeEncodeError` on a `→` character the model used — the same class of bug as the emoji-in-argparse-help crash from stage 1's CLI work. Fixed with a `_print_safe` helper in `cli.py` that falls back to character replacement instead of raising.

**Weights moved off hardcoded constants, and `/validate` actually applies feedback — added 2026-09-05.** Originally, "auto-applying suggestions" was considered and explicitly rejected in favor of a human reading a markdown report and hand-editing `scoring.py`'s constants. That still left a real gap: applying anything meant editing source code and redeploying — not something you can do from your phone. Closed it properly instead of just deciding not to bother:
- **`scoring.py`'s point weights are no longer module constants.** They're a `ScoringWeights` pydantic model (`scoring/models.py`) that every scoring function now takes as a parameter, defaulting to `DEFAULT_WEIGHTS` — which reproduces the exact original hardcoded values, so this refactor changes nothing by itself. The live values are persisted in a new `scoring_weights` singleton DB row (`db/models.py`'s `ScoringWeightsRow`, `db/repository.get_scoring_weights`/`update_scoring_weights`) — a brand-new table, picked up automatically by `Base.metadata.create_all` on the already-deployed DB (unlike a new *column*, which needs the `_ensure_column` workaround used elsewhere).
- **`graph.py`'s `synthesize` node now returns structured suggestions, not just prose** — a strict `json_schema` Mistral call (same pattern as stage 3's analyzer) returns `{patterns_observed, suggestions: [{weight, current_value, new_value, reason}]}`, with `weight` constrained by schema `enum` to `ScoringWeights`'s actual field names so the LLM can't invent one. The prose report is rendered from this same structured data (not a second, separate generation) so the two can never disagree. The structured suggestions are saved to `data/feedback/latest_suggestions.json`, always overwritten by the newest review.
- **Two new Telegram commands close the loop**: `/reviewfeedback` runs the review agent and posts the report (same content `becarscout feedback-review` prints); `/validate` reads `latest_suggestions.json`, applies every suggestion in it via `update_scoring_weights`, confirms exactly what changed, and clears the file (so a repeat `/validate` doesn't reapply the same thing). This is still explicitly opt-in and human-triggered — the design principle is unchanged, only the *mechanism* for "applying" got easier. **Validated live**: seeded 5 synthetic feedback verdicts, ran the real review (Mistral genuinely proposed 4 weight changes with correct reasoning, e.g. raising the warning-light-needs-diagnostic penalty because both disliked cars had it), applied them via `/validate`'s underlying function, and confirmed the DB's live weight actually changed from -20 to -30 — then reset it back to defaults immediately after, since it came from fabricated test data, not real feedback.

**User-adjustable pipeline parameters via Telegram — added 2026-09-05.** A new `settings.py` module (`PipelineSettings`: `radius_km`, `min_price`, `max_price`, `min_year`, `threshold`) persisted the same way as scoring weights (`db/models.py`'s `PipelineSettingsRow`, `db/repository.get_pipeline_settings`/`update_pipeline_settings`). `becarscout run` (what cron actually invokes, with zero flags every time) now resolves each parameter as *explicit CLI flag → stored setting → hardcoded fallback*, in that order — every CLI flag that used to have a hardcoded `default=` now defaults to `None` and cli.py fills in the stored setting when nothing was explicitly passed, so a Telegram-set value takes effect on the *next* hourly run without a redeploy. Five new commands: `/settings` (show everything at once), `/budget <max>` / `/budget <min> <max>` / `/budget off`, `/minyear <year>` / `/minyear off`, `/threshold <n>`, `/radius <km>`.

**`/find`, `/search`, a real command menu, and guided prompts — added 2026-09-05.** Three usability gaps closed at once:
- **`/find`** runs the full pipeline on demand instead of waiting for the next hourly cron tick. Deliberately shells out to `uv run becarscout run` as a background subprocess (`notifier/bot.py`'s `_run_find_pipeline`) rather than calling `run_full_pipeline()` in-process — `do_analyze`/`do_structure` block synchronously per listing, and awaiting them directly inside the bot's own event loop would freeze it for the whole run (no button presses or other commands would work until it finished). This adds no new concurrency risk beyond what already exists: cron's `run` and this `listen` process are already two independent processes sharing the DB via WAL mode (see above), so a third `run` invocation triggered manually is the same situation, just started by a person instead of a clock. The subprocess's stdout is parsed for its `stage: ...` summary lines (`_SUMMARY_LINE_RE`) and relayed back once it exits.
- **`/search <keyword>`** looks through listings already scraped (`db/repository.search_listings` — a case-insensitive match against make/model/title, ordered by score then recency) without scraping anything new — a quick "did I already see a Golf?" check.
- **Telegram's native command-suggestion menu** (`setMyCommands`, wired via `ApplicationBuilder().post_init(...)`) now lists every command with a one-line description when you type `/` in the chat — pure discoverability, no behavior change.
- **Guided prompts**: sending `/budget`, `/minyear`, `/threshold`, or `/radius` with no arguments (or tapping a button under the now-interactive `/settings` card) no longer just prints a usage string — it asks for the value in plain language and applies whatever plain-text message comes back next (`_pending_prompts`, a per-chat in-memory dict, plus a catch-all `MessageHandler` that completes the pending command). Lets someone unfamiliar with the exact argument syntax just answer the bot's question instead of getting the command right on the first try.

**Four more filters — mileage, brand, fuel type, transmission — added 2026-09-05.** `/budget`/`/minyear`/`/threshold`/`/radius` covered price/age/pickiness/search-area, but not the car itself. Added the same layered-default treatment to four more fields the structurer already extracts (`mileage_km`, `make`, `fuel_type`, `transmission` were all sitting unused for filtering purposes):
- `PipelineSettings` gained `max_mileage_km: int | None`, `makes: str | None`, `fuel_types: str | None`, `transmission: str | None` — the latter three stored as raw comma-separated strings (e.g. `"bmw,toyota"`) rather than a real list column, since SQLite has no array type and parsing happens exactly once, at gate time. `PipelineSettingsRow` needed the `_ensure_column` migration treatment (four new columns on an already-deployed table — see stage 6's condition_highlights precedent), not a plain `create_all`.
- **`scoring/gate.py`'s `apply_decision_gate` gained two genuinely different filter *kinds*, and the docstring says so explicitly**: `min_year`/`max_mileage_km` stay soft ceilings — a listing missing that field still passes, same reasoning as the original min_year gate (stage 2 misses fields on plenty of genuine listings; don't punish an extraction gap). `makes`/`fuel_types`/`transmission` are hard "only show me X" filters — a listing with the field *undetected* does **not** pass once one of these is set, the opposite leniency. Reasoning: roughly 64% of listings never get a detected make (Project.md's stage 2 limitations) — if unknown-make listings passed a `/make bmw` filter anyway, the filter would barely narrow anything, defeating its own purpose. Worth remembering if a fifth filter gets added later: the right default depends on whether it's a preference (lenient) or a selection (strict), not a one-size-fits-all rule.
- **Telegram**: `/mileage`, `/make`, `/fuel`, `/transmission` — same guided-prompt-when-no-args pattern as the existing four, plus two new `/settings` button rows. `/fuel` and `/transmission` validate against `structurer.parse.FUEL_TYPES`/`TRANSMISSIONS` (small, fixed sets — reject a typo outright with the valid list). `/make` doesn't reject unknown brands (car names are much more open-ended, and a mistyped-but-close brand should still work as literal text) but does warn ("I don't recognize 'astonmartin' as a brand I track") so a genuine typo doesn't silently filter out everything.
- **CLI**: `score` and `run` both gained matching `--max-mileage-km`/`--makes`/`--fuel-types`/`--transmission` flags, resolved through the same explicit-flag → Telegram-setting → default chain as everything else — no special-casing for the new ones.

**Rewritten for non-technical users — added 2026-09-05.** Every message the bot sends was originally written the way the code itself thinks about the pipeline — "radius", "threshold", "scrape", "score" — fine for the one person who built this, not fine as a message someone else could pick up cold. Reworded every reply (`/settings`, `/budget`, `/minyear`, `/threshold`, `/radius`, `/find`, `/search`, `/validate`) to plain, friendly language with no pipeline jargon, and added `/start`/`/help` — a welcome message explaining what the bot does and pointing at `/settings` — since there was previously no first-contact message at all for someone who'd never used it. `/find`'s completion message got the most substantial change: it used to relay the raw subprocess log lines (`scrape: 20 new listings, 3 price changes`, `score: 20 listings (2 opportunities)`, `notify: 2 sent`) verbatim; `_summarize_find_output` now parses those same lines with fixed regexes and turns them into one plain sentence ("Found 20 new listings. 2 of them looked like a good deal — sent them to you above!"), falling back to a generic "something went wrong" message if none of the expected log lines are found at all (e.g. a stage crashed before logging its summary).

**"Super user experience" pass — added 2026-09-05.** Five specific, scoped improvements, all in `notifier/bot.py`:
- **A bot-wide error handler** (`application.add_error_handler`). Before this, an unhandled exception inside any handler just vanished into the container logs — the user got no message at all, which reads as "the bot is broken" with no signal why. Now it logs the exception and tells the chat "something went wrong, try again."
- **`/cancel`**. Every `_cmd_X` prompt sets a per-chat `_pending_prompts` entry so the next plain-text message is treated as that command's argument (see the earlier settings-prompt work) — but there was previously no way to back out of one. `/cancel` clears it (and any in-progress `/setup`).
- **This required a real return-value contract change**: every promptable `_cmd_X` (`budget`/`minyear`/`threshold`/`radius`/`mileage`/`make`/`fuel`/`transmission`) now returns `bool` — `True` only once a value was actually applied, `False` for a bare prompt or invalid input. `_handle_plain_reply` used to unconditionally pop the pending-prompt entry before calling the handler, which meant a typo during a guided prompt silently killed the prompt state — the user had no arm left to retry against and had to retype the full `/command value`. Now the entry is only cleared on `True`, so an invalid reply just leaves the same prompt active for a retry, and `_handle_plain_reply` uses the same `True` signal to know when to advance a `/setup` wizard.
- **`/setup`**: chains the four core settings (budget → min year → radius → threshold) into one guided flow, reusing each setting's own existing no-args prompt (`_advance_wizard` just calls the next `_cmd_X` with empty args) rather than duplicating prompt text anywhere. `_wizard_queue` (chat id → remaining steps) is the only new state; a chat not in it is simply not mid-setup, so ordinary single-setting edits are untouched. Reachable via `/setup` or the "🚀 Quick setup" button now on `/start`'s welcome message.
- **Quick-pick buttons** for `/budget` (Under €5,000 / €5,000-15,000 / €15,000+) and `/threshold` (😌 Loose / ⚖️ Balanced / 🔥 Strict) — one tap instead of typing a number, for the common cases. Routed through a `qp:` sub-scheme on the existing settings callback (`set:qp:<setting>:<key>`), applied directly via `update_pipeline_settings` rather than round-tripping through each command's text-parsing.
- **`/find` UX**: a resent-every-4s "typing…" chat action for the whole run (Telegram's own indicator only lasts ~5s, so a multi-minute wait needs it repeated or the chat looks frozen), and a `_find_running` set that turns a second `/find` tap mid-run into "still searching" instead of launching a second overlapping `becarscout run` subprocess.

**`/search` time-range filter — added 2026-09-06.** `/search <keyword>` could only match on make/model/title with no sense of recency — a car found an hour ago and one found three weeks ago looked identical in the results. Added an optional trailing range token (`today`, `2days`, `3days`, `week`, mapped to a `since = now() - N days` filter on `ListingRow.scraped_at` in `repository.search_listings`): `/search golf week` narrows an existing search, and a range with *no* keyword (`/search today`) works as "show me everything new" rather than literally searching for the word "today". Quick-pick buttons (📅 Today/2 days/3 days/Last week) are attached to a bare `/search` and to zero-hit results, routed through the existing settings-callback scheme's new `sr:` sub-case; a small per-chat `_last_search_keyword` dict lets a range button re-run the chat's last keyword search without trying to encode arbitrary keyword text into callback_data (which has a 64-byte limit and its own separator conflicts). Landed in the same turn as multi-user support below, so `_format_search_hit`/`_cmd_search` also needed to start showing *the requesting chat's own* score for each hit (via a new `repository.get_user_scores_by_listing_ids` batch lookup) instead of a single shared score value that no longer exists on the listing itself.

**Multi-user support — added 2026-09-06.** Every Telegram command up to this point wrote to a *singleton* row (`id=1`) — one budget, one set of weights, one `TELEGRAM_CHAT_ID` to notify, shared by whoever happened to be talking to the bot. Asked directly: "the chat may be multiuser so each user with its own profile" — fully isolated per person, not just settings. This was the largest architectural change of the project so far; the design that came out of it:

- **What's shared vs. per-subscriber, and why the line is where it is.** Scraping, structuring, and the LLM analyzer stay exactly as they were — one Facebook scrape, one Mistral pass, reused by everyone, because the listings themselves don't depend on who's asking. The market-price *baseline* (comps median/sample/confidence) also stays shared — comps are the same regardless of viewer — but it moved from being computed inline during scoring to its own explicit stage (`resolve_baselines` in `scoring/pipeline.py`, `do_resolve_baselines`/`becarscout baseline` in `cli.py`), gated by a new `ListingRow.baseline_computed_at` column, so this network-bound Playwright work still happens exactly once per listing no matter how many subscribers exist. What genuinely differs per person — condition-signal weights and the gate (threshold, min year, mileage, brand, fuel, transmission) — moved to a new `UserListingScoreRow` table (`db/models.py`), keyed by `(chat_id, listing_id)`, holding `price_component`/`condition_component`/`score`/`above_threshold`/`reasoning_json`/`condition_highlights_json`/`scored_at`/`notified_at`. The old columns of those same names on `ListingRow` are left in place (SQLite can't cheaply drop columns) but nothing reads or writes them anymore — same tolerance the project already had for the stray leftover `feedback_verdict` column from the `version1` branch (see the SQLite-corruption notes below).
- **The one deliberate exception: search radius stays global.** Budget, year, mileage, brand, fuel, and transmission can all be personal *filters* applied after the fact, since price/year/mileage/make/fuel/transmission are all known per listing. Radius can't be — there's no per-listing distance-from-hub figure to filter by afterward, so personalizing it would mean literally re-scraping once per distinct radius value, multiplying cost with subscriber count. `/radius` still works from Telegram; it just changes one shared value (`GlobalScrapeSettingsRow`, a new singleton, replacing radius's old home on the now-per-chat `PipelineSettingsRow`) instead of something personal — the wording in `/radius`'s own reply says so explicitly, since it's a real, easy-to-miss asymmetry with every other filter. Budget also changed *in kind*, not just in storage: it used to narrow the live Facebook scrape query (`--min-price`/`--max-price`); now it's a post-scrape gate filter like mileage, letting each subscriber have their own range against one shared, broader scrape.
- **Subscribing is implicit.** A new `SubscriberRow` table (chat_id, created_at) is the list `do_score`/`do_notify` loop over. Rather than requiring `/start` specifically, `notifier/bot.py` registers a `TypeHandler(Update, ...)` at `group=-1` — python-telegram-bot processes handler groups in ascending order and a lower-numbered group doesn't stop the update from reaching the next one, so this genuinely runs as middleware before every command/callback/message, calling `repo.ensure_subscriber` unconditionally. Anyone who sends the bot anything becomes a subscriber; no separate registration step to forget.
- **Feedback and mem0 were already halfway there.** `feedback_agent/memory.py`'s mem0 integration always took a `user_id` parameter — pre-multiuser it was hardcoded to a constant `OWNER_USER_ID = "owner"`. Swapping that constant for `str(chat_id)` was the entire change needed to make `find_similar_feedback`/`store_feedback_memory`/`get_all_feedback_memories` genuinely per-subscriber — mem0's own filtering already does the isolation. The review agent (`feedback_agent/graph.py`) gained a `chat_id` field on its `ReviewState` threaded through every node; its markdown reports now land as `review_<chat_id>_<timestamp>.md` instead of colliding on one filename. `/validate`'s "last review's suggestions" moved off a single global `data/feedback/latest_suggestions.json` file onto a new `PendingSuggestionRow` table (chat_id → JSON), since per-chat state belongs alongside per-chat settings/weights now, not scattered across per-chat filenames.
- **The CLI lost some flags, on purpose.** `becarscout score`/`notify`/`run` used to take `--threshold`/`--min-year`/etc. as one-shot overrides; with N subscribers each having their own values, a single CLI override applying to everyone silently defeats the personalization it just built, so those flags are gone — `score`/`notify` now take no gate arguments at all, reading each subscriber's own stored settings/weights internally. `feedback-review` gained a required `--chat-id` (there's no single default "whose feedback" anymore); `rescore` gained an optional one (default: every subscriber).
- **Migrating a real, already-populated deployment without a notification flood.** The actual risk here wasn't code correctness in the abstract, it was the *existing* single-user deployment: naively shipping this would silently reset a real person's carefully-configured budget/weights back to defaults, and worse, every listing already scored under the old model would look "never scored for this subscriber" and queue up for re-notification — plausibly dozens of already-seen cards flooding back into their chat at once. `db/engine.py`'s `_migrate_singleuser_to_subscriber` (called from `_ensure_initialized`, idempotent, a no-op once a chat_id has its own subscriber row) reads `TELEGRAM_CHAT_ID` from the environment once, subscribes that chat, copies its legacy singleton settings/weights into real per-chat rows, and — critically — copies every already-scored `ListingRow` into a `UserListingScoreRow` for them with `notified_at` carried over intact. **Validated against a copy of the real production DB** (never against the live file itself, consistent with this project's established "don't run host-side scripts against the live DB" rule): 321 already-scored listings, 38 already-notified — post-migration, `get_unnotified_opportunities` for the real chat_id correctly returned 0, and the subscriber's settings/weights matched exactly what was in the legacy singleton row. The temporary DB copy was deleted immediately after.
- **New tests**: `tests/db/test_engine.py` (new file) covers the migration directly against an isolated engine — idempotency, leaving an already-migrated chat's real settings alone, carrying over `notified_at`, and the env-var-missing/malformed no-op paths. `tests/db/test_repository.py` was substantially rewritten for the per-chat/shared split (isolation-between-chats is now an explicitly tested property, not just an implicit one).
- **Confirmed live after deploying**: the migration log line on the real container read exactly `Migrated legacy single-user settings/weights/scores to subscriber <real chat_id> (321 already-scored listing(s) carried over)` — matching the dry-run count precisely — and the very next scheduled run completed scrape → structure → analyze → baseline → score → notify with zero errors, `score: 15 listings (0 opportunities)` (per-subscriber scoring genuinely ran) and no re-sent notifications.

**`/name` — added 2026-09-06.** A direct follow-up question after multi-user shipped: "how do you know each user, and how do they set a name?" — the honest answer at the time was "Telegram's chat_id, and they can't." Fixed by adding a `name` column to `SubscriberRow` (another `_ensure_column` migration, since `subscribers` was already a live table) plus `repo.get_subscriber_name`/`set_subscriber_name`. A brand-new chat's very first interaction (`/start`, or `/help`) is now a plain "what should I call you?" prompt *before* the usual welcome text/Quick-setup button — answering it (via `_cmd_name`, wired into the same `_PROMPTABLE_COMMANDS`/pending-prompt machinery as every other setting) is what unlocks the full welcome message, so name-collection genuinely comes first for a new person, not just cosmetically. A chat that already has a name just gets greeted by it ("👋 Hi Badr!") and skips straight to the welcome text. `/name <text>` changes it anytime, and it shows up in `/settings`. Deliberately *not* wired into every other command as a nag/gate — only `/start`/`/help` ask, keeping the rest of the bot fully usable for someone who never bothers to introduce themselves.

**Commands without the leading "/", and `/weights` for hand-tuning the scoring engine — added 2026-09-06.** Two follow-ups from the same conversation:
- **No-slash commands.** Every registered command now also works as plain text — `settings`, `budget 15000`, `cancel` — not just `/settings`/`/budget 15000`/`/cancel`. Implemented as a lookup table, `_TEXT_COMMANDS` (built after every handler function it references exists, so it lives right after `_cmd_start`'s definition near the bottom of `bot.py`), mapping each command word to the exact same handler function `CommandHandler` uses. The catch-all `MessageHandler` for non-command text now points at a new `_handle_plain_text`, which checks the first word of the message against `_TEXT_COMMANDS` before falling back to the existing pending-prompt logic (`_handle_plain_reply`) — so a command word always wins over whatever prompt happens to be pending, deliberately matching how a real `/slash` command already behaves (Telegram's `CommandHandler`s are registered independently of `_pending_prompts` and would win regardless). This incidentally fixes a small rough edge for free: typing `cancel` (no slash) while a `/budget` prompt is armed now actually cancels it, instead of being read as an invalid budget value that just re-arms the same prompt.
- **`/weights` (also `/showall`)**: the condition-signal point values (`ScoringWeights` — gearbox/engine issue severity, accident damage, warning lights, timing belt, inspection, service history, export listings, minimum plausible car price) were only ever changeable indirectly, by running `/reviewfeedback` and hoping it happened to suggest the field you wanted changed, then `/validate`-ing it. `/weights` lists every one of these 16 values for the requesting subscriber with its current point value, and a button per field that prompts for a new number and applies it immediately via the same `repo.update_scoring_weights` `/validate` already used — reusing the existing `_pending_prompts` mechanism with a `wt:<field>` key instead of a plain setting name, since there are 16 of these instead of one slot per command. This makes the scoring engine genuinely user-tunable in real time, not just retroactively from whatever a feedback review happened to notice.

**Real bug found 2026-09-05, fixed**: `becarscout listen` (the standing process that captures Telegram thumbs up/down presses) was never actually started inside the Docker container — `docker/entrypoint.sh` only ran the hourly `becarscout run` pipeline. This meant every 👍/👎 pressed on a live opportunity card went nowhere: nothing was polling Telegram for the button press, so it wasn't recorded to `feedback.jsonl`, DB, or mem0, even though all of that code worked correctly when run manually. Fixed by starting `becarscout listen` in the background from `entrypoint.sh` alongside cron (its own log, `data/feedback_listener.log`, also tailed into `docker compose logs`). This also means the container now genuinely runs two long-lived processes concurrently for the first time (the hourly pipeline and the standing listener) — not multi-threaded within either one (see below), but real concurrent access to the same SQLite DB from two OS processes, which prompted also switching SQLite to WAL journal mode + a 5s busy-timeout in `db/engine.py` (readers and a writer no longer block each other; a genuine write/write collision retries briefly instead of raising "database is locked" immediately).

**Is any of this actually multi-threaded/concurrent? Answered honestly:**
- **Within one pipeline run**: no. Scraping visits listing detail pages sequentially (see stage 1's known limitations), stage 3's Mistral calls are sequential with a deliberate delay, and `resolve_baselines` resolves each listing's price baseline one at a time (`scoring/pipeline.py`) — correctness and staying clear of rate limits mattered more than throughput for an hourly personal job, so none of this was parallelized. Per-subscriber scoring (`do_score`'s loop over subscribers) is a plain Python loop too, but it's pure computation with no I/O, so this isn't a throughput concern the way the shared stages are.
- **Across processes**: yes, for real, as of this fix — the hourly `run` and the standing `listen` process both run continuously inside the same container and can touch the DB/mem0 at the same moment. The DB is now WAL-mode to handle that. **mem0's local Chroma store is not given the same treatment** — chromadb's persistent (file-based) client is designed around single-process use, and `listen` (writing a feedback memory) and `run`'s `notify` step (reading via `find_similar_feedback`) are now two separate processes pointed at the same on-disk `data/mem0/chroma/`. At this project's actual volume (one button press at a time, at most a few notify-time lookups per hour) a genuine collision is unlikely, but it's a real, undocumented-until-now risk rather than something proven safe — worth watching `data/feedback_listener.log` for Chroma errors, and revisiting (e.g. running Chroma as a small local server instead of embedded-file mode) if one ever shows up.

**Known limitations / how to enhance further:**
- `_MIN_FEEDBACK_FOR_REVIEW = 5` is an arbitrary floor, not a statistically-derived one — with real usage volume, this is worth revisiting (a higher floor for a more reliable trend, or a lower one just to see the report take shape sooner).
- The review agent looks at *all* accumulated feedback every time, with no decay — a preference from months ago carries the same weight as one from yesterday. A real enhancement here would timestamp-weight or window the query (e.g. "feedback from the last 90 days") once there's enough history for that to matter.
- Pattern detection is single-pass (`get_all_feedback_memories` + one Mistral call) rather than iterative — the agent doesn't re-query mem0 mid-analysis to dig into a pattern it half-notices (e.g. "let me check if high-mileage diesels specifically are disliked more than high-mileage petrols"). A genuinely iterative LangGraph agent (a loop node that decides whether it has enough evidence yet, re-searching mem0 with a more specific query if not) would produce sharper, better-evidenced suggestions — reasonable v2 scope, held back for now since the volume of real feedback doesn't yet justify the extra complexity.
- No feedback on *rejected* listings (below the decision-gate threshold, never sent to Telegram) — the agent only ever sees what you explicitly rated, not silent near-misses. Widening this would mean sending borderline listings anyway with a lower-confidence label, which is a real product trade-off against "low noise over completeness" (Project.md's own design principle), not just an engineering task.
- `mem0`'s own optional NLP extras (spaCy-based entity/lemma matching) aren't installed (`pip install mem0ai[nlp]` — logs a harmless warning on every call) — fine at this data volume; worth reconsidering only if search quality becomes a problem with hundreds+ of stored memories.

## Design principles
- **LLM does interpretation, not judgment.** Free text → structured facts is the one thing worth using an LLM for; the actual buy/no-buy scoring stays deterministic and inspectable.
- **Everything the system flags should be traceable** back to a specific phrase or field — no unexplained scores.
- **Belgium-first.** Get the market model, language handling, and paperwork terms right for one country before generalizing.
- **Low noise over completeness.** Better to miss a borderline listing than to erode trust in the Telegram alerts.

## Infrastructure — ✅ Done (2026-09-04)
The pipeline runs unattended, hourly, in a Docker container.

**Database.** Replaced the per-stage JSONL files with SQLite (`src/becarscout/db/`) — one denormalized `listings` table, one row per listing, gaining columns as it moves through stages 1→6. This is what makes hourly cron cheap: `get_listings_needing_structuring`/`_analysis`/`_scoring` each query for rows that haven't reached that stage yet (a plain `WHERE ... IS NULL`), so a listing scraped and processed last hour is never re-sent to Mistral, re-scraped for comps, or re-scored on the next run — only genuinely new listings do any work. `notified_at` on the same table replaced the separate `sent_ids.json` file the notifier used to track. The pydantic models from stages 1–6 didn't change at all; the DB is purely a persistence detail behind `db/repository.py`, converting to/from those same models.

**Real incident, 2026-09-05: `data/becarscout.db` corrupted (`sqlite3.DatabaseError: database disk image is malformed`).** Happened during a heavy live-debugging session where the host was running `uv run becarscout ...` commands and ad-hoc Python scripts directly against the DB *while the Docker container was also running its own hourly cycle against the exact same file* — SQLite's WAL mode handles concurrent access from multiple connections reasonably well on a native filesystem, but this project's `data/` volume is a Docker Desktop bind mount from a Windows host into a Linux container, and cross-boundary file-locking semantics over that kind of mount are known to be less reliable than native locking, especially under sustained concurrent read/write from both sides at once. Diagnosed the damage before touching anything further: `PRAGMA integrity_check` failed outright, but `SELECT listing_id FROM listings` (no other columns) succeeded for all 230 rows — the corruption was confined to specific rows' data pages, not the whole table. Checked each row individually to isolate exactly which ones (9 of 230, all from the same narrow window of concurrent writes) actually failed to read, then rebuilt a fresh database from the 221 fully-readable rows (`Base.metadata.create_all` on a new file, re-inserting only the confirmed-good rows) rather than trying to force-repair the corrupted pages in place. Verified the rebuilt file with `PRAGMA integrity_check` before swapping it in, and kept the original corrupted file as a dated backup rather than deleting it. **Real, accepted cost**: the 9 lost rows included 3 that had just been successfully notified moments earlier — their DB record (including `notified_at`) is gone, so if the scraper encounters those exact listings again, they'll look brand-new and could cause one duplicate notification each; not a systemic issue, just a one-time consequence of this specific incident. **Lesson for future sessions**: never run host-side scripts or CLI commands directly against `data/becarscout.db` while the container is also running — either stop the container first (`docker compose stop`), or do host-side testing against a copy of the DB, not the live file.

**Known limitation, found 2026-09-05 while fixing the price-change-detection bug above**: incremental processing means a fix to `scoring.py`/`baseline.py`/`analyzer/schema.py` only ever changes how *newly-processed* listings score — a row that already has `scored_at` set keeps its old (possibly now-known-wrong) score forever, since nothing re-queries `WHERE scored_at IS NOT NULL`. Confirmed live: the original 1986 Ford F-150 comp-matching bug (stage 4 notes above) was fixed in code days earlier, but this exact row in the DB still showed the old +72 score until something incidentally reset its `scored_at` to NULL. Fixed the same day: `becarscout rescore` (`db/repository.reset_scoring_for_rescore`) nulls `scored_at` for every analyzed listing, so the next `becarscout score` re-evaluates all of them with whatever the current code computes. Deliberately leaves `notified_at` untouched — re-scoring alone shouldn't cause a re-notification for something already sent.

**`becarscout run`** (`cli.py`) chains scrape → structure → analyze → score → notify in one call, with each stage independently wrapped in try/except — if Facebook's markup breaks the scraper mid-run, already-processed backlog still moves through structure/analyze/score/notify instead of the whole hourly run being a no-op.

**Docker.** `Dockerfile` bases on plain `python:3.12-slim` + `uv run --no-project playwright install --with-deps chromium` (resolves the right OS packages for whatever Chromium version the pinned `playwright` package needs, rather than betting on a matching pre-built `mcr.microsoft.com/playwright/python` tag existing). Cron (the real `cron` package, not a Python sleep loop — installed in the image) fires `becarscout run` hourly via `docker/crontab`; `docker/entrypoint.sh` also runs it once immediately at container startup, then hands off to `cron -f` as PID 1 so `docker stop`/logs behave correctly. One non-obvious fix along the way: cron doesn't inherit the container's environment, so `entrypoint.sh` snapshots `printenv` to a file that `docker/run_pipeline.sh` sources on every tick — otherwise `MISTRAL_API_KEY`/`TELEGRAM_BOT_TOKEN` would be invisible to the hourly job despite being set on the container.

**What can't run in Docker: `becarscout login`.** It opens a real, visible browser window for a human to log into Facebook — that's structurally impossible in a headless container. Login must happen once on a machine with a display (the host), which creates `data/.session/profile/`; `docker-compose.yml` mounts the whole `data/` directory as a volume, so the container picks up that already-authenticated session (plus the SQLite DB, the pricing cache, and pipeline logs) without ever needing a display itself.

**Real bugs found by actually running the container against live data** (not by inspection — every one of these only showed up once the whole thing ran for real end-to-end):
- `python-telegram-bot`'s HTTP client logs full request URLs at INFO level, which for Telegram means the bot token appears in plaintext — including what would have been the persisted `data/pipeline.log`. Fixed by dropping `httpx`'s logger to WARNING in `cli.py`'s `main()`.
- **The scraper had no idea what the DB already knew about.** The first live container run was about to spend ~10 minutes re-visiting the detail page of every listing found in that hour's grid search — including ones already fully processed in a previous run — before the DB-level dedup in `upsert_raw_listings` would finally discard them as duplicates. That defeated a good chunk of the whole point of moving to a database. Fixed by having `do_scrape` fetch known listing_ids from the DB first and passing them to `scrape_belgium_cars(known_ids=...)`, which now skips the detail-page visit entirely for anything already known.
- **Two Docker build-layer bugs**, both from the deps-before-source layering meant to keep the slow Chromium install cached separately from code changes: `uv run playwright install` failed because a bare `uv run` tries to sync/build the local project too, and the project's source wasn't copied in yet at that layer (fixed with `uv run --no-project`); `uv sync --frozen` after copying source failed because `pyproject.toml` references `README.md` as the package readme, which had been excluded via `.dockerignore` for no real reason (fixed by not excluding it).
- **A live Telegram `TimedOut`** on the very first real notify call, even though the same run's Mistral and 2dehands.be calls succeeded fine. Diagnosed layer-by-layer from inside the running container (DNS resolved fine, raw TCP connected in 80ms, a plain `httpx` GET succeeded) before finding it was specific to `python-telegram-bot`'s default timeouts (5s connect/read, a notably tight 1s pool timeout) — a manual retry of the exact failing call succeeded instantly. Fixed with longer timeouts (20s) and a 3-attempt retry with backoff around the connection itself, tracking already-sent listing_ids across attempts so a retry never double-sends. Even so: the real safety net is architectural, not the retry — since delivery status lives in the DB (`notified_at`), a `notify` failure just means those opportunities get picked up and sent on the *next* hourly run instead of being lost, which is exactly what was observed happening correctly during validation.
- **Not a code bug, but a real incident**: `docker compose config` was run once to sanity-check the compose file, and it echoes fully-resolved environment values — printing `MISTRAL_API_KEY`, `TELEGRAM_BOT_TOKEN`, and `TELEGRAM_CHAT_ID` in plaintext into this session's own output. Combined with the earlier httpx logging leak (caught and fixed, but only after it had already printed the token once), that's two real secrets that ended up in this conversation's transcript. Both were rotated afterward. Lesson for future sessions: never run `docker compose config` (or anything else that echoes resolved env values) once real secrets are in `.env`.

**Status as of 2026-09-05: the container is live** (`docker compose up -d`, `restart: unless-stopped`), running the full pipeline hourly. First real run surfaced 8 genuine opportunities, delivered to Telegram successfully.

## Stack
- **Scraping**: Playwright (Python)
- **Storage**: SQLite (`data/becarscout.db`, via SQLAlchemy) for listings through every stage; a small JSON comps cache (`data/pricing_cache/`) and a feedback JSONL (`data/feedback/feedback.jsonl`) alongside it. Postgres was the original fallback plan but SQLite is genuinely sufficient at personal-project scale and keeps the Docker setup to one container.
- **LLM**: Mistral API (`ministral-8b-latest`, via the `mistralai` SDK) for the extraction step only, strict JSON schema output
- **Scoring**: plain Python, no ML — see stage 4 notes
- **Delivery**: python-telegram-bot
- **Scheduling**: real cron inside the Docker container, hourly
- **Feedback agent (stage 7)**: LangGraph (small graph orchestration) + mem0 (local, Chroma + FastEmbed) for feedback memory, `litellm` as the glue letting mem0 use Mistral instead of OpenAI internally — see stage 7 notes above.
- **Tests**: pytest (`uv run pytest`), added 2026-09-05 alongside the first regression tests (`tests/structurer/`, `tests/pricing/`) — no test setup existed before those two bugs, so there's not yet coverage for every stage, just the ones that have had a real, reported bug (later extended to `tests/notifier/`, `tests/feedback_agent/` alongside stage 7's build).
